## Scope and privacy invariants of #20

| Invariant                                                                 | Where it is enforced and tested                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| No mutable global principal                                               | per-request principal in both apps; ACCESS-01 "overlapping A/B requests" fails when a module-level "last principal" replaces the per-request map (ACCEPTANCE.md §4)                                                                                                                                                                  |
| No body, `ownerId` or `user_metadata` authority                           | OAUTH-03 (metadata and look-alike claims ignored); ACCESS-01 "forged owner arguments grant nothing"; RLS-03 "claims" (a forged `request.jwt.claims` grants nothing)                                                                                                                                                                  |
| No service-role or secret key in the web bundle or the MCP iframe         | `apps/web/src/test/config.test.ts` (publishable key only); DEPLOY-01 secret scanners (`tools/deploy/deploy-01-scanners.test.ts`) on the built bundles; DEPLOY-02 on the deployed ones; the View only receives tool results through the host bridge, and the MCP server passes neither the token nor the client on (MCP_SERVER.md §1) |
| A web session token cannot call the MCP, an MCP token cannot call the API | OAUTH-01 client binding; OAUTH-02 wire tests; on the real provider: OAUTH-04 "web session token refused at /mcp" and "OAuth token refused by the REST API"                                                                                                                                                                           |
| Logout and token-expiry claims match the implemented provider policy      | Sign-out ends this browser's session only and does not revoke issued access tokens, which stay valid until `exp` (WEB_AUTH.md; AUTH_MCP_OAUTH.md §4). AUTH-UI-I01 records both on the real project: the refresh token refused after sign-out, and the API answer to the old access token                                             |
| No teams, billing or social scope                                         | nothing to test: no such code exists                                                                                                                                                                                                                                                                                                 |

## Completion

#20 is complete when, at one release commit:

1. the local evidence above passes (`pnpm test`, `pnpm test:integration`,
   `pnpm check:arch`, and the CI run of that commit);
2. the cloud suites AUTH-UI-I01 and OAUTH-04 pass against the deployed apps
   and the real Supabase project, or each blocked step is recorded with its
   cause (for example supabase/auth#2820) and the owner has decided what it
   means for the release;
3. the target-host check is recorded, or recorded as not run with the reason
   (no authorized host access is a limitation, never a pass);
4. the owner sign-offs of RELEASE_CHECKLIST.md step 10 that concern auth
   (audience mode, OAuth host path, dynamic registration, documented limits)
   are recorded in EVIDENCE.md.

Until the release record in EVIDENCE.md holds these results, #20 stays open.
